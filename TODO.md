## Разрывы линий на графике: события одного цикла округляются к разным минутам

Найдено 18 сентября 2026 при разборе «пропусков DHT11» в проекте monitoring.
Данные в облаке полные — разрывы появляются только при отрисовке.

**Где.** `src/model/series.ts:105`, `seriesFromEvents`:

```ts
// Events collected in one cycle are milliseconds apart; rounding to a common
// tick lets them share an x position instead of producing interleaved gaps.
const t = Math.round(event.observed_at / alignSeconds) * alignSeconds;   // alignSeconds = 60
```

**Что изменилось в бэкенде.** Допущение из комментария больше не верно. Агент
читает источники по очереди, и у каждого события своя отметка observed_at.
Чтение DHT11 (`source=room`) идёт с повторами через 2 с и может занять до ~10 с,
статус агента (`source=agent`) пишется после него. Снимок камеры идёт на 30 с
позже, но на график не попадает. Контракт описан в README бэкенда, раздел API v1.

**Как проявляется.** Если цикл начинается около :28–:30 секунды минуты, `cpu`
округляется к текущей минуте, а `room` и `agent` — к следующей. В
`buildChartData` у каждой линии в соседней точке оси оказывается `null`, и uPlot
рисует разрыв. За сутки 17–18 сентября так разъехались 15 % циклов — все случаи,
когда первая попытка чтения DHT11 не удалась.

**Как исправить.** Группировать события цикла, а не округлять время: например,
отсортировать события и начинать новый тик, когда событие отстоит от первого
события текущего тика больше чем на 60 с. Тиком цикла брать время его первого
события (при желании — округлённое до минуты).

Подгонять observed_at в агенте под общую метку не нужно: это исказило бы время
измерения.

**Тест.** Цикл с `cpu` в `T0 + 28 с`, `room` в `T0 + 34 с`, `agent` в `T0 + 34.1 с`:
все три должны оказаться на одном x. Два цикла с разницей 600 с — на разных.
Существующие тесты — `tests/series.test.ts`.
